# PowerStig Windows 复制、配置与运行指南

最后更新：2026-10-14

本文面向需要把当前项目中更新后的 PowerStig 带到其他 Windows 计算机或其他项目中使用的人员。

如果希望目标机器只接收一个文件，优先使用第 12 节的单文件离线包；第 2 至第 7 节保留手动复制目录的方式，便于调试或定制。

## 1. 文件职责

部署工具由三个必须放在同一目录的文件组成：

| 文件 | 是否必须 | 用途 |
|---|---:|---|
| `PowerStig.Windows.Common.psm1` | 是 | 公共实现：系统识别、STIG 版本映射、依赖处理、DSC 模块暂存、MOF 编译 |
| `Deploy-PowerStigWindows.ps1` | 部署时必须 | 编译并应用配置；`-WhatIf` 不应用 STIG，也不修改执行策略 |
| `Test-PowerStigWindowsCompliance.ps1` | 检查时必须 | 不应用 STIG 基线；输出 JSON 和逐资源 CSV |

不要只复制某一个 `.ps1`。两个入口脚本都会加载同目录中的 `PowerStig.Windows.Common.psm1`。

可选文件：

- 组织设置 XML：生产环境建议提供，路径通过 `-OrgSettingsPath` 传入。
- 本文档：方便目标机器操作人员查阅。
- `.gitignore`：仅在把工具目录放入 Git 项目时有用。

## 2. 推荐目录结构

在目标机器或外部项目中建立以下目录：

```text
C:\PowerStigDeployment\
├─ Scripts\
│  ├─ PowerStig.Windows.Common.psm1
│  ├─ Deploy-PowerStigWindows.ps1
│  └─ Test-PowerStigWindowsCompliance.ps1
├─ Modules\
│  ├─ PowerStig\
│  │  └─ <PowerStig版本>\
│  │     ├─ PowerStig.psd1
│  │     ├─ PowerStig.psm1
│  │     ├─ DSCResources\
│  │     ├─ Module\
│  │     └─ StigData\
│  └─ <PowerStig 所需的依赖模块>\
└─ Configuration\
   └─ OrgSettings.xml       # 可选，但生产环境推荐
```

`Modules\PowerStig\<PowerStig版本>` 必须来自本项目构建或导出的模块，不能只复制 `STIGS` 原始文件。当前版本是 `4.30.0`；运行时使用的是已经转换并打包到 `StigData` 中的数据。

## 3. 从当前项目复制哪些内容

### 3.1 复制脚本

从当前项目复制：

```text
PowerStig\Tools\Deployment\PowerStig.Windows.Common.psm1
PowerStig\Tools\Deployment\Deploy-PowerStigWindows.ps1
PowerStig\Tools\Deployment\Test-PowerStigWindowsCompliance.ps1
```

把这三个文件放到目标目录的 `Scripts` 文件夹中，且不要改变它们之间的相对位置。

### 3.2 复制 PowerStig 模块

把当前项目中的完整版本目录复制到目标模块根。以当前 `4.30.0` 为例：

```text
源：PowerStig\output\PowerStig\4.30.0
目标：C:\PowerStigDeployment\Modules\PowerStig\4.30.0
```

必须复制整个版本目录，包括 `DSCResources`、`Module` 和 `StigData`。

如果当前项目还没有 `output\PowerStig\4.30.0`，先按项目构建/导出流程生成模块，再进行复制。

### 3.3 依赖模块的两种准备方式

联网机器推荐让脚本下载精确版本依赖：首次运行添加 `-InstallDependencies`。依赖会保存到 `-ModuleRoot` 指定的目录。

离线机器需要提前把 `PowerStig.psd1` 中 `RequiredModules` 列出的精确版本一起复制到 `Modules`。目录格式必须为：

```text
Modules\<模块名>\<版本>\模块文件
```

不要只复制模块清单文件，也不要混用其他版本替代清单要求的版本。

## 4. 运行前配置

1. 使用管理员身份打开 Windows PowerShell 5.1。也可以从 PowerShell 7 启动，脚本会自动转到 Windows PowerShell 5.1。
2. 确认操作系统是 Windows Server 2019、2022、2025、Windows 10 或 Windows 11。
3. 确认 `Modules\PowerStig\<PowerStig版本>\PowerStig.psd1` 存在。当前版本示例为 `Modules\PowerStig\4.30.0\PowerStig.psd1`。
4. 生产环境准备组织设置 XML，并由安全负责人审核。
5. 如果机器通过域组策略强制执行 PowerShell 执行策略，应先由管理员配置允许 DSC 模块运行的策略；脚本不会覆盖 `MachinePolicy`。

系统与 STIG 映射集中维护在 `PowerStig.Windows.Common.psm1` 的 `$script:TargetCatalog` 中。

## 5. 首次安全验证

进入脚本目录：

```powershell
Set-Location C:\PowerStigDeployment\Scripts
```

先运行部署预演。该命令会准备依赖、暂存 LCM 模块并编译 MOF，但不会应用任何 STIG 设置：

```powershell
.\Deploy-PowerStigWindows.ps1 `
    -ModuleRoot C:\PowerStigDeployment\Modules `
    -InstallDependencies `
    -StageModulesForDsc `
    -WhatIf
```

成功条件：

- 命令退出码为 `0`。
- `Artifacts\<计算机名-时间>\localhost.mof` 存在。
- 最新 `Logs\Deploy-PowerStig-*.summary.json` 中 `Succeeded=true`、`Applied=false`。

## 6. 正式部署

自动识别本机系统；服务器会自动判断域控制器 `DC` 或成员/独立服务器 `MS`：

```powershell
.\Deploy-PowerStigWindows.ps1 `
    -ModuleRoot C:\PowerStigDeployment\Modules `
    -StageModulesForDsc `
    -ConfigureExecutionPolicy `
    -OrgSettingsPath C:\PowerStigDeployment\Configuration\OrgSettings.xml
```

如果首次预演已经完成依赖下载，可以省略 `-InstallDependencies`。建议仍保留 `-StageModulesForDsc`，确保 LCM 使用的模块与本次部署一致。

显式指定 Windows Server 2022 成员服务器：

```powershell
.\Deploy-PowerStigWindows.ps1 `
    -Target WindowsServer2022 `
    -ServerRole MS `
    -ModuleRoot C:\PowerStigDeployment\Modules `
    -StageModulesForDsc `
    -ConfigureExecutionPolicy `
    -OrgSettingsPath C:\PowerStigDeployment\Configuration\OrgSettings.xml
```

注意：正式部署会调用 `Start-DscConfiguration` 并修改系统安全设置。必须先在测试环境使用 `-WhatIf` 验证。

## 7. 运行合规检查

合规检查不会应用 STIG 基线：

```powershell
.\Test-PowerStigWindowsCompliance.ps1 `
    -ModuleRoot C:\PowerStigDeployment\Modules `
    -StageModulesForDsc `
    -ConfigureExecutionPolicy `
    -OrgSettingsPath C:\PowerStigDeployment\Configuration\OrgSettings.xml
```

部署和检查必须使用相同的 `OrgSettings.xml`，否则检查基线与部署基线可能不同。

检查并非对文件系统完全只读：它会生成日志和参考 MOF；使用 `-StageModulesForDsc` 时会把模块复制到 LCM 可见目录；使用 `-ConfigureExecutionPolicy` 时可能把 `LocalMachine` 执行策略改为 `RemoteSigned`。这些操作用于准备检查环境，不会执行 `Start-DscConfiguration` 或应用 STIG 设置。

退出结果：

| 结果 | JSON 字段 | 含义 |
|---|---|---|
| 合规 | `Succeeded=true`, `InDesiredState=true` | 检查成功且全部资源合规 |
| 不合规 | `Succeeded=true`, `InDesiredState=false` | 检查成功，但存在不合规资源；进程退出码为 1 |
| 执行失败 | `Succeeded=false`, `Error` 非空 | 模块、权限、策略或 DSC 执行失败 |

自动化系统不应只依据退出码区分“不合规”和“脚本错误”，应同时读取最新 JSON 摘要。

## 8. 输出位置

默认在 `Scripts` 目录生成：

```text
Artifacts\              # 部署 MOF
ComplianceArtifacts\    # 检查 MOF
Logs\                    # 文本日志、Transcript、JSON、CSV
```

重要文件：

- `Deploy-PowerStig-*.summary.json`：部署结果和 MOF 路径。
- `Test-PowerStig-*.summary.json`：检查状态、合规数量、不合规数量和错误。
- `Test-PowerStig-*.resources.csv`：逐资源检查结果。
- `*.transcript.log`：完整 PowerShell 会话记录。

可用 `-OutputRoot` 和 `-LogRoot` 把产物写入集中日志目录。

## 9. 常见问题

### 提示找不到公共模块

确认三个脚本文件位于同一目录，且文件名为 `PowerStig.Windows.Common.psm1`。

### 提示找不到指定版本的 PowerStig

确认公共模块中配置的版本与复制的目录一致，并确认传入的 `-ModuleRoot` 是 `PowerStig` 文件夹的上一级。例如当前版本清单在：

```text
C:\PowerStigDeployment\Modules\PowerStig\4.30.0\PowerStig.psd1
```

则参数应为：

```powershell
-ModuleRoot C:\PowerStigDeployment\Modules
```

### 提示缺少依赖

联网时增加 `-InstallDependencies`；离线时从联网机器复制完整的精确版本依赖目录。

### 提示执行策略为 Restricted

增加 `-ConfigureExecutionPolicy`，或让域管理员配置批准的机器策略。如果 `MachinePolicy` 已由组策略设置，必须修改组策略，脚本不会覆盖它。

### 日志中显示规则被 Skipped

通常是没有提供组织值。生成并审核 `OrgSettings.xml`，然后部署和检查都传入同一个 `-OrgSettingsPath`。

### 检查时报 `CimException: Invalid name`

这表示 Windows DSC/LCM 在执行 `Test-DscConfiguration` 时拒绝了某个 CIM 或资源名称。错误末尾指向检查脚本的 `throw` 行并不代表该行是根因，应查看同一次运行的 JSON 和 transcript。

Windows Server 2025 DC 规则 `V-278138` 的 DISA 检查路径为 `%windir%\NTDS\*.*`。`AccessControlDSC 1.4.3` 不支持通配 NTFS 路径：当目录中有多个文件时，它会把文件名数组传给 `FileSecurity`，并抛出 `.ctor(...): Invalid name`。修正版 PowerStig 不再把此规则编译成 `NTFSAccessEntry`，而是在 MOF 编译时输出警告并要求手工审核。不要把路径简单改成 `%windir%\NTDS` 后强制应用 ACL，这可能删除域控数据库目录所需的其他权限。

手工审核时应按照 `V-278138` 原始 STIG 内容，读取注册表 `HKEY_LOCAL_MACHINE\System\CurrentControlSet\Services\NTDS\Parameters` 中实际数据库和日志位置，再分别检查对应文件 ACL。此规则不会影响其他无通配符的 NTFS 规则继续部署。

新版本检查摘要包含 `FailureStage`、`ExceptionType`、`ErrorDetails` 和 `ScriptStackTrace`。在目标机执行：

```powershell
$extractRoot = Get-ChildItem "$env:ProgramData\PowerStigOffline" -Directory |
    Sort-Object LastWriteTime -Descending |
    Select-Object -First 1

$summary = Get-ChildItem "$($extractRoot.FullName)\Scripts\Logs\Test-PowerStig-*.summary.json" |
    Sort-Object LastWriteTime -Descending |
    Select-Object -First 1

Get-Content $summary.FullName -Raw | ConvertFrom-Json |
    Select-Object FailureStage, ExceptionType, Error, ErrorDetails, ScriptStackTrace |
    Format-List

Get-DscLocalConfigurationManager |
    Format-List ConfigurationMode, LCMState, LCMStateDetail, RebootNodeIfNeeded

Get-DscConfigurationStatus -All |
    Select-Object -First 5 Status, Type, StartDate, DurationInSeconds, Error |
    Format-List
```

同时查看 transcript 中错误前最后一个 `[[资源类型][V-规则号]...]` 记录，它通常能定位触发异常的资源。不要仅因为此错误就删除 LCM 配置；先保留 JSON、transcript、参考 MOF 和资源 CSV，再判断是资源名称、模块版本、待重启状态还是损坏的 LCM 状态。

## 10. AI 维护边界

为减少以后 AI 修改时的重复和偏差，按以下职责修改：

- 新增系统版本或修改 STIG 映射：只改 `PowerStig.Windows.Common.psm1` 中的 `$script:TargetCatalog`。
- 修改模块查找、依赖下载、LCM 暂存、执行策略或 MOF 结构：改公共模块。
- 修改部署行为、确认逻辑或部署摘要：改 `Deploy-PowerStigWindows.ps1`。
- 修改检查结果、CSV 字段或不合规退出行为：改 `Test-PowerStigWindowsCompliance.ps1`。
- 公共行为不得复制回两个入口脚本。

每次修改后至少执行：

1. Windows PowerShell 5.1 解析三个文件。
2. 对全部支持目标运行部署脚本 `-WhatIf`。
3. 在测试机运行一次检查脚本并验证 JSON、CSV 和 MOF。
4. 确认检查脚本中没有 `Start-DscConfiguration`。

## 11. 升级 PowerStig 版本

### 11.1 先区分两种更新

- **只更新 STIG 数据，不提升 PowerStig 模块版本**：运行 STIG 更新工具后，继续导出为当前版本。例如仍然使用 `4.30.0`。
- **发布新的 PowerStig 模块版本**：除了更新 STIG 数据，还要提升模块清单版本。例如从 `4.30.0` 提升到 `4.31.0`。

如果需要把新旧模块同时保留、进行回滚或正式发布，建议提升版本。仅在本地快速验证最新 STIG 数据时，可以保持当前版本并使用 `-Force` 覆盖导出目录。

### 11.2 更新并检查 STIG 数据

把新的 DISA ZIP 放入仓库的 `PowerStig\STIGS`，然后在 `PowerStig` 仓库根目录运行：

```powershell
Set-Location D:\12PowerStig\PowerStig

# 只预检，不修改 source\StigData
.\Tools\StigUpdate\Invoke-StigUpdate.ps1 -WhatIf

# 正式转换并更新 source\StigData
.\Tools\StigUpdate\Invoke-StigUpdate.ps1 -Verbose
```

确认 `Tools\StigUpdate\last-update-report.json` 中：

- 顶层 `Succeeded` 为 `true`。
- 每个输入包的 `Status` 为 `Converted`。
- 没有阻止发布的 `QualityFindings`。

不要直接修改 `source\StigData\Processed`。转换问题应修复在 XCCDF 同名 `.log`、转换器或 `stig-update.json` 中，然后重新运行更新工具。

### 11.3 提升模块版本时修改两处

如果要从 `4.30.0` 发布为 `4.31.0`，先修改模块清单：

```powershell
# source\PowerStig.psd1
ModuleVersion = '4.31.0'
```

再修改部署工具使用的固定版本：

```powershell
# PowerStig.Windows.Common.psm1
$script:PowerStigVersion = [version] '4.31.0'
```

这两个值必须一致：

```powershell
$manifest = Import-PowerShellDataFile .\source\PowerStig.psd1
Import-Module .\Tools\Deployment\PowerStig.Windows.Common.psm1 -Force

if ([version] $manifest.ModuleVersion -ne (Get-PowerStigRequiredVersion)) {
    throw 'source manifest 与部署工具的 PowerStig 版本不一致。'
}
```

如果不提升模块版本，不需要修改这两处。

### 11.4 方法 A：快速导出模块

适用于本地验证、外部项目目录和单文件离线包。它会把当前 `source` 完整复制到版本化目录，不运行完整测试或生成 NuGet 包。

在仓库根目录运行：

```powershell
Set-Location D:\12PowerStig\PowerStig

.\Tools\StigUpdate\Export-PowerStigModule.ps1 `
    -Destination .\output `
    -Force
```

导出版本来自 `source\PowerStig.psd1` 的 `ModuleVersion`。如果版本是 `4.31.0`，预期生成：

```text
output\PowerStig\4.31.0\PowerStig.psd1
output\PowerStig\4.31.0\PowerStig.psm1
output\PowerStig\4.31.0\DSCResources\
output\PowerStig\4.31.0\Module\
output\PowerStig\4.31.0\StigData\
```

`-Force` 会替换同一版本的已有导出目录。需要保留旧内容时，先提升版本或把旧目录备份到其他位置。

### 11.5 方法 B：正式构建模块

适用于发布前验证以及需要 NuGet 包的场景。首次在一台开发机上构建时，先恢复构建依赖：

```powershell
Set-Location D:\12PowerStig\PowerStig

# 首次运行，下载 InvokeBuild、ModuleBuilder、Pester 和模块依赖
.\build.ps1 -ResolveDependency -Tasks noop
```

只构建版本化模块目录：

```powershell
.\build.ps1 -Tasks build
```

执行默认构建和测试：

```powershell
.\build.ps1
```

构建模块并生成 NuGet 包：

```powershell
.\build.ps1 -Tasks pack
```

`build.yaml` 已配置 `VersionedOutputDirectory: true`，并会复制 `DSCResources`、`Module` 和 `StigData`。构建后应在 `output\PowerStig\<版本>` 找到模块；`pack` 还会在 `output` 下生成 `.nupkg`。

如果构建提示缺少 `Invoke-Build`、`ModuleBuilder`、Pester 或 DSC 模块，重新运行：

```powershell
.\build.ps1 -ResolveDependency -Tasks noop
```

然后再执行 `build` 或 `pack`。

### 11.6 为离线包准备精确依赖

`New-PowerStigOfflinePackage.ps1` 要求 `output` 同时包含 PowerStig 和清单中的全部精确依赖。联网开发机可以运行：

```powershell
$moduleRoot = Join-Path $PWD 'output'
$manifest = Import-PowerShellDataFile .\source\PowerStig.psd1

foreach ($dependency in $manifest.RequiredModules) {
    $requiredVersion = [version] $dependency.ModuleVersion
    $expectedPath = Join-Path $moduleRoot "$($dependency.ModuleName)\$requiredVersion"

    if (-not (Test-Path $expectedPath)) {
        Save-Module `
            -Name $dependency.ModuleName `
            -RequiredVersion $requiredVersion `
            -Path $moduleRoot `
            -Force
    }
}
```

### 11.7 验证新模块

先确认模块清单和关键目录完整：

```powershell
$version = '4.31.0'
$modulePath = ".\output\PowerStig\$version"

@(
    "$modulePath\PowerStig.psd1"
    "$modulePath\PowerStig.psm1"
    "$modulePath\DSCResources"
    "$modulePath\Module"
    "$modulePath\StigData"
) | ForEach-Object {
    if (-not (Test-Path $_)) { throw "缺少构建产物：$_" }
}
```

使用新模块查看可用 STIG：

```powershell
$env:PSModulePath = "$(Resolve-Path .\output);$env:PSModulePath"
Import-Module PowerStig -RequiredVersion 4.31.0 -Force

Get-Stig -ListAvailable |
    Sort-Object Technology, TechnologyVersion, TechnologyRole, Version |
    Format-Table Technology, TechnologyVersion, TechnologyRole, Version
```

确认公共模块的 `$script:TargetCatalog` 引用的每个 STIG 版本都出现在输出中。如果 DISA 数据版本发生变化，同时更新对应 `StigVersion`。

最后运行部署预演、检查和单文件打包：

```powershell
# 不应用配置，只验证 MOF 编译
.\Tools\Deployment\Deploy-PowerStigWindows.ps1 `
    -ModuleRoot .\output `
    -WhatIf

# 生成新版本单文件离线包
.\Tools\Deployment\New-PowerStigOfflinePackage.ps1 `
    -ModuleRoot .\output `
    -Force
```

在测试机运行新包的 `-Mode Deploy -WhatIf` 和默认只读检查后，再进入生产部署。

### 11.8 完整升级检查清单

1. 更新并转换 STIG ZIP，确认更新报告成功。
2. 如需发布新模块版本，同时修改 `source\PowerStig.psd1` 和公共模块中的版本。
3. 使用快速导出或正式构建生成 `output\PowerStig\<版本>`。
4. 检查新版本 `PowerStig.psd1` 的 `RequiredModules`，准备所有精确版本依赖。
5. 检查 `$script:TargetCatalog` 中的 STIG 数据版本是否存在于新模块。
6. 对全部支持目标运行 `Deploy-PowerStigWindows.ps1 -WhatIf`。
7. 在测试机运行 `Test-PowerStigWindowsCompliance.ps1`，验证 MOF、JSON 和 CSV。
8. 重新生成单文件离线包并执行 `-Mode Deploy -WhatIf`。
9. 验证通过后再删除旧版本目录；回滚验证完成前保留旧版本。

脚本有意固定版本，不会自动选择“机器上最高版本”。这样可以避免目标机器安装了未经验证的新版本后，生产基线在没有审核的情况下发生变化。DSC 配置中的 `RequiredVersion` 会由公共模块自动生成，不需要再修改第二处代码。

## 12. 生成并使用单文件离线包

`New-PowerStigOfflinePackage.ps1` 会把以下内容压缩并写入一个自解压 `.ps1`：

- 部署入口、检查入口和公共模块。
- 公共模块中配置的 PowerStig 版本。
- `PowerStig.psd1` 要求的全部精确版本依赖。
- 本使用指南。
- 可选的组织设置 XML。

### 12.1 在开发机生成

生成单文件包前，必须先准备 `PowerStig\output`。**不强制运行完整的 `build.ps1`**；构建器只要求以下内容存在：

```text
output\PowerStig\<公共模块中配置的版本>\PowerStig.psd1
output\<依赖模块名>\<PowerStig.psd1 要求的精确版本>\
```

如果刚更新了 STIG 数据，最短流程是在仓库根目录执行：

> 仅把文件放入 `STIGS` 后运行 `Export-PowerStigModule.ps1` **不会应用新数据**。导出脚本只复制现有的 `source`；必须先运行 `Invoke-StigUpdate.ps1`，把 `STIGS` 中的原始文件转换到 `source\StigData`。

```powershell
Set-Location D:\12PowerStig\PowerStig

# 1. 预检 STIG 转换，不修改 source
.\Tools\StigUpdate\Invoke-StigUpdate.ps1 -WhatIf

# 2. 正式转换 STIGS 中的文件并更新 source\StigData
.\Tools\StigUpdate\Invoke-StigUpdate.ps1 -Verbose

# 3. 确认更新报告成功后，把更新后的 source 导出到 output\PowerStig\<版本>
$report = Get-Content .\Tools\StigUpdate\last-update-report.json -Raw |
    ConvertFrom-Json

if (-not $report.Succeeded) {
    throw 'STIG 更新失败，请检查 last-update-report.json，不能继续导出。'
}

.\Tools\StigUpdate\Export-PowerStigModule.ps1 `
    -Destination .\output `
    -Force

# 4. 下载 output 中缺少的精确版本依赖；已有依赖不会重复下载
$manifest = Import-PowerShellDataFile .\source\PowerStig.psd1
foreach ($dependency in $manifest.RequiredModules) {
    $version = [version] $dependency.ModuleVersion
    $expectedPath = Join-Path $PWD "output\$($dependency.ModuleName)\$version"

    if (-not (Test-Path $expectedPath)) {
        Save-Module `
            -Name $dependency.ModuleName `
            -RequiredVersion $version `
            -Path .\output `
            -Force
    }
}

# 5. 生成单文件离线包
.\Tools\Deployment\New-PowerStigOfflinePackage.ps1 `
    -ModuleRoot .\output `
    -Force
```

因此完整数据流是：

```text
STIGS 原始文件
    -> Invoke-StigUpdate.ps1
    -> source\StigData
    -> Export-PowerStigModule.ps1
    -> output\PowerStig\<版本>
    -> New-PowerStigOfflinePackage.ps1
    -> 单文件离线包
```

完成“导出”只表示新 STIG 数据已经进入 `output` 模块，**不会修改任何 Windows 配置**。要应用到系统，还必须选择以下一种方式：

```powershell
# 开发机或手动目录方式：先预演，再移除 -WhatIf 正式应用
.\Tools\Deployment\Deploy-PowerStigWindows.ps1 `
    -ModuleRoot .\output `
    -StageModulesForDsc `
    -WhatIf

# 目标机单文件方式：先预演，再移除 -WhatIf 正式应用
.\PowerStig-Windows-Offline-4.30.0.ps1 `
    -Mode Deploy `
    -WhatIf
```

只有部署命令不带 `-WhatIf` 时，脚本才会调用 DSC 修改系统。生产部署前应先检查预演生成的 MOF，并提供经过审核的 `OrgSettings.xml`。

如果用于正式发布，先执行完整构建和测试，再生成单文件包：

```powershell
Set-Location D:\12PowerStig\PowerStig

# 首次在开发机运行时恢复构建依赖
.\build.ps1 -ResolveDependency -Tasks noop

# 正式构建并运行测试
.\build.ps1

# 如需同时生成 NuGet 包，改用：.\build.ps1 -Tasks pack

# 检查并补齐 output 中的运行依赖后生成单文件包
.\Tools\Deployment\New-PowerStigOfflinePackage.ps1 `
    -ModuleRoot .\output `
    -Force
```

正式构建不一定会在 `output` 中留下单文件包需要的全部运行依赖。运行构建器前，仍应执行上面的依赖检查/下载代码，或者确认所有依赖目录已经存在。

如果 `output` 已经包含正确版本的 PowerStig 和全部依赖，可以直接运行：

```powershell
Set-Location PowerStig\Tools\Deployment
.\New-PowerStigOfflinePackage.ps1 -Force
```

默认输出：

```text
Packages\PowerStig-Windows-Offline-<版本>.ps1
```

如果希望把经过审核的组织设置一起放入单文件：

```powershell
.\New-PowerStigOfflinePackage.ps1 `
    -OrgSettingsPath C:\Baseline\OrgSettings.xml `
    -Force
```

也可以指定其他模块根或输出文件：

```powershell
.\New-PowerStigOfflinePackage.ps1 `
    -ModuleRoot C:\PowerStigDeployment\Modules `
    -OutputPath C:\Release\PowerStig-Offline.ps1 `
    -Force
```

构建器会在生成前检查：

- 公共模块配置的 PowerStig 版本是否存在。
- 导出模块清单中的 `ModuleVersion` 是否与公共模块一致。
- `RequiredModules` 中的每个精确版本依赖是否存在。

缺少或版本不一致时会停止，不会生成不完整的离线包。输出包含载荷 SHA-256，目标机每次重新解压前也会校验该哈希。

### 12.2 复制到目标机

只需要复制生成的一个文件，例如：

```text
PowerStig-Windows-Offline-4.30.0.ps1
```

不需要另外复制 `Modules`、公共模块或两个入口脚本。运行后默认解压到：

```text
%ProgramData%\PowerStigOffline\<版本>-<载荷哈希前12位>
```

相同包再次运行会复用已校验的解压目录。使用 `-ForceExtract` 可以强制重新解压。

### 12.3 默认执行只读检查

以管理员身份运行：

```powershell
.\PowerStig-Windows-Offline-4.30.0.ps1 `
    -ConfigureExecutionPolicy
```

默认 `Mode` 是 `Check`，不会应用 STIG 配置。离线启动器会解压载荷并暂存 DSC 模块；只有传入 `-ConfigureExecutionPolicy` 时才可能修改本机执行策略。不合规时退出码为 `1`，应查看解压目录 `Scripts\Logs` 中的 JSON 和 CSV。

`-WhatIf` 只用于 `-Mode Deploy`。Check 模式本身不会调用 `Start-DscConfiguration`，因此运行 `-Mode Check -WhatIf` 不会增加额外保护，启动器会忽略该 `-WhatIf`。

如果包内没有组织设置，可以使用目标机上的外部文件：

```powershell
.\PowerStig-Windows-Offline-4.30.0.ps1 `
    -Mode Check `
    -OrgSettingsPath C:\Baseline\OrgSettings.xml `
    -ConfigureExecutionPolicy
```

### 12.4 安全部署预演

```powershell
.\PowerStig-Windows-Offline-4.30.0.ps1 `
    -Mode Deploy `
    -WhatIf
```

该命令解压模块并编译 MOF，但不应用设置。

### 12.5 正式部署

```powershell
.\PowerStig-Windows-Offline-4.30.0.ps1 `
    -Mode Deploy `
    -ConfigureExecutionPolicy
```

只有显式指定 `-Mode Deploy` 且没有 `-WhatIf` 才会调用部署入口并修改系统。

部署入口使用 `Start-DscConfiguration -Wait`，会等待 DSC 执行完成，并在返回前自动进行一次合规测试。因此看到部署摘要中 `Succeeded=true`、`Applied=true`、`InDesiredState=true`、`RebootRequested=false` 后，通常不需要额外等待，可以立即使用同一个单文件运行默认的 `Check` 模式：

```powershell
.\PowerStig-Windows-Offline-4.30.0.ps1 `
    -Mode Check `
    -ConfigureExecutionPolicy
```

以下情况应先处理，再运行最终检查：

- 部署摘要中 `RebootRequested=true`，或者部署日志、DSC 资源结果、Windows Update 显示需要重启：先重启，再检查。
- 修改了服务、角色、功能或安全策略，而操作系统明确要求重启：先重启。
- 计算机受域组策略管理：等待正常策略刷新，或由管理员执行 `gpupdate /force` 后再检查；域策略也可能覆盖本地 DSC 设置。
- 部署脚本仍在运行：不要并行启动检查，等待它完全退出。

不建议无条件等待固定分钟数。部署脚本正常退出且没有重启或策略刷新要求时，立即检查即可。部署和检查必须使用相同的 `OrgSettings.xml`、目标、服务器角色和模块版本。

### 12.6 只解压不运行

```powershell
.\PowerStig-Windows-Offline-4.30.0.ps1 -Mode ExtractOnly
```

该模式适合检查包内版本、模块清单和脚本。也可以通过 `-ExtractRoot C:\PowerStigExtracted` 指定解压位置。
